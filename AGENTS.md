# Repository Guidelines

## Project Structure & Module Organization

`BackupZCrypt.sln` contains six .NET 10 projects. `BackupZCrypt.Domain` holds the archive domain and does no I/O: the algorithm identifiers and the cipher and key-derivation contracts in `Algorithms`, and the archive format in `Archive` (format constants and cryptographic sizes, manifest model and codec, file naming, key schedule, chunk crypto, and manifest path rules). `BackupZCrypt.Application` is organized by feature, each folder keeping its interfaces beside their implementations: `Backup` (the `IBackupOperations` use cases a front end calls, their requests, outcome, and validator), `Manifest`, `Benchmark`, `Passwords`, `Settings`, the strategy registry, the compression and chunking ports, and the catalog of algorithms a front end offers in `Algorithms`, the chunked backup engine in `Engine`, the file-system ports in `FileSystem`, and what features share (results, messages, path normalization, and progress) in `Common`. A contract lives in the innermost layer whose code consumes it: the cipher and key-derivation contracts the key schedule and manifest codec use stay in Domain, and every other port (compression, chunking, file system, settings) lives in Application. `BackupZCrypt.Infrastructure` implements them, grouped like the ports it serves: `Algorithms`, `FileSystem`, and `Settings`. Dependency injection lives in `BackupZCrypt.Composition`. Project references point inward only: Domain references no project, Application references only Domain, Infrastructure references only Application, Composition references Application and Infrastructure, Desktop references Application and Composition, and the test project references all five; `LayerDependencyTests` enforces these rules. Inside Application, features depend only downward, with `Algorithms`, `Common`, and `FileSystem` at the bottom and `Engine` below the use-case features; `FeatureDependencyTests` pins these edges and the Application features and Domain areas Infrastructure and Desktop use, and `DomainPurityTests` keeps Domain free of I/O. The Avalonia/MVVM client is in `BackupZCrypt.Desktop`, with UI code split among `Views`, `ViewModels`, `Models`, `Controls`, `Behaviors`, `Converters`, `Animations`, `Styles`, `Assets` (icon geometries), `Platform` (Avalonia adapters for the clipboard and folder-picker ports the ViewModels own), `Presentation` (localization and display formatting), and `Resources`; `DesktopLayeringTests` pins the edges between these folders, keeps `ViewModels`, `Models`, `Presentation`, and `Resources` free of Avalonia, and lets only the root reference Composition. Tests are centralized in `BackupZCrypt.Test/Unit` and `BackupZCrypt.Test/Integration`; shared fixtures belong in `Common`. Committed on-disk format archives live in `BackupZCrypt.Test/TestData/OnDiskFormatArchives`; `BackupZCrypt.Test/Tools` holds their shared definitions and the explicit-only generator that rewrites them. Treat `dist`, `bin`, and `obj` as generated output.

## Build, Test, and Development Commands

- `dotnet restore BackupZCrypt.sln` restores centrally versioned NuGet packages.
- `dotnet build BackupZCrypt.sln` compiles every project; analyzers, code style, nullable checks, and warnings-as-errors are enabled.
- `dotnet run --project BackupZCrypt.Desktop` launches the desktop application locally.
- `dotnet test BackupZCrypt.sln` runs the complete xUnit v3 suite.
- `dotnet format whitespace BackupZCrypt.sln --verify-no-changes` verifies formatting before review.
- `dotnet run --file scripts/render-icon.cs` regenerates `BackupZCrypt.png` and `BackupZCrypt.ico` from `BackupZCrypt.Desktop/Resources/BackupZCrypt.svg`; edit the SVG, not the rasters. The sidebar logo is the `AppLogoImage` drawing in `App.axaml` and must be kept in step with the SVG by hand.

Use the .NET 10 SDK or newer. Publishing and distributable packaging are handled by the release workflow, not normal builds.

## Coding Style & Naming Conventions

Follow standard C# formatting with four-space indentation, file-scoped organization where already used, nullable annotations, and implicit usings. Use PascalCase for types, methods, properties, and public members; camelCase for parameters and locals; prefix interfaces with `I`. Keep filenames aligned with their primary type (`ManifestService.cs`) and use descriptive suffixes such as `*Service`, `*Validator`, `*Strategy`, and `*ViewModel`. Add XML documentation to new public APIs. Do not suppress analyzer findings without a narrow, documented reason.

## Testing Guidelines

Use xUnit v3 and NSubstitute. Name test classes `TypeNameTests` and test methods after observable behavior. Place isolated tests under `Unit/<Layer>`, mirroring the folder of the type under test, cross-cutting suites under `Unit/Architecture` and `Unit/Format`, and filesystem or end-to-end scenarios under `Integration`. Tests must be deterministic, locale-independent, and own and clean up temporary files. CI requires at least 90% line, branch, and method coverage of the `Application`, `Composition`, `Domain`, and `Infrastructure` assemblies (see `BackupZCrypt.Test/CodeCoverage.config` and the local gate in `README.md`); cover new behavior, failure paths, archive compatibility, and security-sensitive edge cases. Regenerate the format fixtures only for a deliberate format change with `dotnet run --project BackupZCrypt.Test -- -explicit only -class "*OnDiskFormatFixtureGenerator"`, and review the resulting diff.

## Commit & Pull Request Guidelines

Use Conventional Commits, consistent with history: `feat:`, `fix:`, `perf:`, `refactor:`, `chore:`, `ci:`, or `bump:` for dependency updates. Mark breaking changes with `!` in the subject; the release workflow reads only commit subjects, so a `BREAKING CHANGE:` footer alone does not bump the major version. Only breaking, `feat:`, `fix:`, and `perf:` commits publish a release. Branch from `develop` and open pull requests against `develop`; `master` is reserved for releases. PRs should explain intent and risk, link relevant issues, list verification commands, and include screenshots for Avalonia UI changes. Run build, tests, and the whitespace check before requesting review.

## Security & Configuration

Never commit passwords, keys, plaintext backup data, or user settings. Preserve archive-format compatibility and path-confinement checks; cryptography, manifest, and restore changes require focused regression tests. Update shared package versions only in `Directory.Packages.props`.
